## Context

Weekly activity plans are currently generated by calling an LLM API inside `generateWeeklyPlan()` in `llm.service.js`. The LLM is prompted with the user's profile, activity history, and the list of available activities; it returns a JSON blob representing 7 days.

This approach has several constraints:
- LLM latency (1–5 s per call) degrades UX
- Non-determinism makes plans hard to test and audit
- API failures fall back to a random "template-fallback" that ignores the user's fitness goal and activity level entirely
- Token cost scales with the number of available activities

The algorithm proposed here replaces the LLM call **only** for the weekly plan generation path. The SSE streaming endpoint, regenerate-day, and swap endpoints will also be updated to use the same algorithm. The per-day `activityPlan/generator.js` (used by a different route) is out of scope.

## Goals / Non-Goals

**Goals:**
- Generate a 7-day plan deterministically using only profile data and the `activities` table
- Respect `fitness_goal` via `goal_tags` filter on `activities`
- Respect `activity_level` by capping the calorie ceiling per activity
- Enforce exactly 2 rest days per week, randomized position
- Assign total daily duration tiers: 20 / 40 / 60 / 80 / 100 min based on intensity level
- Pack each active day with 3–4 activity sets that fit the tier budget
- Keep the same API request/response shape (`{ days: [...] }`) — no frontend changes
- Keep toggle-complete, swap, and get operations untouched

**Non-Goals:**
- Personalizing rest day placement based on workout history
- Progressive overload or week-over-week progression
- Refactoring the per-day `activityPlan/generator.js` LLM flow
- Changing the DB schema

## Decisions

### D-01 · Activity Level → Base Calorie Ceiling

Map `activity_level` enum values to a max-calorie-per-activity ceiling for filtering:

| Activity Level | Max cal/activity |
|---|---|
| sedentary | 80 |
| lightly_active | 150 |
| moderately_active | 250 |
| very_active | 400 |
| extra_active | ∞ (no cap) |

**Why**: Keeps low-activity users away from high-intensity activities that list large calorie burns without imposing arbitrary intensity labels. The `estimated_calories` field on `activities` reflects a standard-duration session, making it a reasonable proxy for exercise intensity.

**Alternative considered**: Filter by an explicit `intensity` column — rejected because `activities` has no such column.

### D-02 · Daily Duration Tiers per Intensity Level

| Sedentary | Lightly Active | Moderately Active | Very Active | Extra Active |
|---|---|---|---|---|
| 20 min/day | 40 min/day | 60 min/day | 80 min/day | 100 min/day |

**Why**: Progressive workload. Sedentary users should not be given 60-minute days. The tiers can be tuned without changing API contracts.

### D-03 · Set Count and Perfect Fit Guarantee

Each active day picks randomly between 3 and 4 activities from the filtered pool. 
To guarantee a "Perfect Fit" for the daily tier budget:
- **Underflow**: If total duration falls short of the tier budget, the activities' durations are scaled up proportionally to exactly hit the tier.
- **Overflow**: If an activity exceeds the remaining budget, it is added, but its duration is prorated (scaled down) so the daily total exactly matches the budget. No further activities are added.

**Why**: This ensures every active day perfectly hits the workload target without messy fractions or failing constraints.

### D-04 · Rest Day Placement

Two days out of 7 are randomly designated as rest days. The remaining 5 days are active.

**Why**: Fixed 2-rest-day rule per the algorithm spec. Random placement avoids always resting on the same days.

### D-05 · Module Location

New file: `backend/src/services/activityPlan/weeklyPlanAlgorithm.js`

The controller will import this instead of `generateWeeklyPlan` from `llm.service.js` for the plan-generation path. All other LLM service imports in the controller (cache helpers, lock, swap, regenerate-day) are preserved until those handlers are similarly migrated (out of scope).

**Why**: Isolating the algorithm in a dedicated file matches existing module conventions (`activityPlan/generator.js`, `activityPlan/validator.js`) and makes the LLM → algorithm switch a targeted, reviewable diff.

### D-06 · Calories Burned Computation

Reuse the existing `computeCaloriesBurned(dbActivity, durationMin)` formula:
```
caloriesBurned = round(estimated_calories / duration_min * durationMin)
```

### D-07 · Activity Repetition Constraints

Allow activity repetition across the week, but **never** allow the same activity twice in a single day. If the valid pool is exhausted before hitting 3 activities, the day simply ends with fewer activities (and D-03 scaling ensures the budget is still hit).

**Why**: Prevents "repetitive hell" (e.g., getting "Walking" 3 times in one day) while ensuring a small fallback pool doesn't break generation.

### D-08 · Synchronous SSE Stream Trap

The algorithm is instantaneous. For the `/api/weekly-plans/generate-stream` endpoint, we will immediately send a single `{ type: 'done', plan: fullPlan }` payload. No artificial chunking or delays will be introduced.

**Why**: Keeps the backend clean and honest. If the frontend parser breaks on an immediate `done` without prior chunks, it should be fixed on the frontend.

## Risks / Trade-offs

- **Risk**: Filtered activity pool is empty (e.g., no activities match `fitness_goal` + calorie ceiling) → **Mitigation**: Fall back to all activities filtered only by calorie ceiling; if still empty, use all activities. Log a warning.
- **Risk**: Activity pool is very small (< 3 activities) → **Mitigation**: Enforce the "unique per day" rule (D-07). The algorithm will safely yield fewer activities and scale their durations to meet the budget.
- **Risk**: Regenerate-day and swap still call LLM helpers in `llm.service.js` → **Mitigation**: Out-of-scope for this change; the controller `generate` and `generateStream` handlers are the only entry points updated here.

## Migration Plan

1. Implement `weeklyPlanAlgorithm.js` with full unit tests
2. Update `weeklyPlan.controller.js` `generate()` and `generateStream()` to call the new algorithm
3. Remove the `generateWeeklyPlan` import (and any SSE-specific wiring) from the controller — leave `getCachedPlan`, `setCachedPlan`, `clearCachedPlan`, `acquireLock`, `swapActivity`, and `regenerateDay` imports intact
4. Deploy — no DB migration needed
5. Rollback: revert controller changes; the algorithm module has no side effects on its own
