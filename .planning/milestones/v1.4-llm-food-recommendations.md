## Overview

LLM generates 7-day meal plans constrained to the user's existing food database. Users can view an AI-suggested weekly meal plan, log individual days to their food diary, and regenerate single days when needed — all with rate-limited API access and automatic fallback if the LLM is unavailable.

### Phase 19: Core Meal Plan Service

**Goal**: Backend service can validate LLM output, fuzzy-match food names, recalculate calories, and generate fallback plans
**Depends on**: Phase 18
**Plans**: 1 plan

Plans:

- [x] 19-01: Meal plan service with validation, fuzzy matching, generation pipeline

**Details:**
- `mealPlan.repository.js`: `findByUserAndWeek`, `upsertPlan`, `markItemsLogged`
- `validateMealPlanStructure()` — 8 validation checks (7-day count, date sequence, 4 meals, valid meal_types, 1-4 items per meal, portion 10-500g, calorie 80-120%, valid food_id/food_name)
- `fuzzyMatchFoodName()` — 4-stage cascade: exact → case-insensitive/substring → Levenshtein ≤ 3 → none

- `generateFallbackMealPlan()` — template-based 7-day plan using 6-8 diverse ingredients per category rotation
- `regenerateDay()` — single-day regeneration with merge into existing plan
- Lean dependency injection pattern for profile/food/log fetchers

## Key Decisions

- Reused existing `openai`, `node-cache`, `express-rate-limit` — zero new packages
- Meal plan tables mirror `weekly_plans` structure exactly (JSONB `plan_data`)
- `getCachedPlan` imported from `llm.service.js` at controller level to avoid circular dependency
- Rate limits: 5/15min generate, 3/30min regenerate, 30/15min log — mirrors v1.3 activity plan limits
- Frontend follows same pattern as WeeklyPlanPage (state machine, DayCard template)
- Per-meal partial logging via optional `mealType` query param
- Correction loop max 2 attempts before template fallback
- Fuzzy match threshold: Levenshtein ≤ 3
