# Test All Backend Endpoints + Frontend Integration

## Objective

Test every backend API endpoint end-to-end against a real MySQL database running via Podman, and verify the frontend API layer correctly communicates with the backend.

**Why this matters:** All 16 endpoints across 4 route groups (auth, profile, food, activities) need verified HTTP contracts — request shapes, response formats, auth requirements, and error handling. Without these tests, regressions go undetected.

**What we need:**
- A Podman MySQL instance with seeded data from `backend/db/init.sql`
- Backend integration tests (supertest + Jest) covering every endpoint
- Frontend API layer tests (Vitest) exercising each API function against the running backend

**File:** `backend/tests/integration/api.test.js`

### Action


**Step B — Create `backend/tests/integration/helpers.js`** containing:

1. **`startDatabase()`** — Runs Podman MySQL using docker-compose.yml:
   ```js
   // podman-compose up -d mysql (or docker compose up -d mysql)
   // Wait for healthcheck with mysqladmin ping retry (30s timeout)
   ```

2. **`stopDatabase()`** — Tears down:
   ```js
   // podman-compose down (or docker compose down)
   ```

3. **`createTestUser(agent)`** — Registers a test user, returns extracted JWT cookie value from Set-Cookie header using supertest's `agent` (cookie jar):
   ```js
   // POST /api/auth/register { email, password, pdpConsent }
   // Return agent with cookies preserved for subsequent requests
   ```

4. **`seedTestData(agent)`** — Creates a profile and logs sample food entries so read endpoints return data.

**Step C — Create `backend/tests/integration/api.test.js`** with Jest `describe` blocks:

**`describe('Auth Endpoints')`:**
- `POST /api/auth/register` with valid data → 201 + cookie set
- `POST /api/auth/register` with missing email → 400 VALIDATION_ERROR
- `POST /api/auth/register` with missing pdpConsent → 400 VALIDATION_ERROR
- `POST /api/auth/register` with duplicate email → 400/409 error
- `POST /api/auth/login` with valid credentials → 200 + cookie set
- `POST /api/auth/login` with wrong password → 401 AUTHENTICATION_ERROR
- `POST /api/auth/login` with non-existent email → 401 AUTHENTICATION_ERROR
- `POST /api/auth/logout` → 200 + cookie cleared
- `GET /api/auth/me` without token → 401 AUTHENTICATION_ERROR
- `GET /api/auth/me` with token → 200 + `{ id, email, pdp_consent, created_at }`

**`describe('Profile Endpoints')`:**
- `POST /api/profile` with valid data → 201 + `{ profile, bmi, bmiCategory, tdee, tdeeRange, calorieTarget }`
- `POST /api/profile` without auth → 401
- `POST /api/profile` with missing weightKg → 400
- `GET /api/profile` with existing profile → 200 + full profile object
- `GET /api/profile` before creating → 404
- `PUT /api/profile` with updated weight → 200 + recalculated bmi/tdee

**`describe('Food Endpoints')`:**
- `GET /api/food/search?q=chicken` → 200 + array of matching foods
- `GET /api/food/search?q=a` (single char) → 400 VALIDATION_ERROR
- `GET /api/food/search?q=ZZZZNOTEXIST` → 200 + empty array
- `POST /api/food` with valid custom food → 201 + food object with `is_custom: true`
- `POST /api/food` with empty name → 400 VALIDATION_ERROR
- `POST /api/food/log` with seeded foodId + portion → 201 + log entry
- `POST /api/food/log` with customFoodName + calories → 201
- `POST /api/food/log` with invalid mealType → 400
- `POST /api/food/log` with portion > 5000 → 400
- `GET /api/food/summary?date=TODAY` → 200 + `{ date, totalConsumed, calorieTarget, remaining, isExtremeDeficit }`
- `GET /api/food/logs?date=TODAY` → 200 + array of log entries
- `GET /api/food/history?days=7` → 200 + array of daily totals
- `GET /api/food/recent` → 200 + array of recently logged foods

**`describe('Activity Endpoints')`:**
- `GET /api/activities/recommendations` → 200 + `{ activities, count }`
- `GET /api/activities` → 200 + `{ activities, total }`

Use supertest's `agent` (superagent) which preserves cookies across requests:

## Task 2: Frontend API Layer Integration Test

**File:** `frontend/src/__tests__/api-integration.test.js`

### Action

Create a Vitest integration test that exercises every frontend API module against the running backend. Uses `beforeAll`/`afterAll` to manage the test lifecycle.

**Test structure:**

```js
// frontend/src/__tests__/api-integration.test.js
import { describe, it, expect, beforeAll, afterAll } from 'vitest';

// API modules (all use credentials: 'include' for cookie-based auth)
import { register, login, logout, getMe } from '../features/auth/api/authApi.js';
import { createProfile, getProfile, updateProfile } from '../features/profile/api/profileApi.js';
import { searchFoods, createCustomFood, logFood, getDailySummary, getDailyLogs, getLogHistory, getRecentFoods } from '../features/food-log/api/foodLogApi.js';
import { getRecommendations, getAllActivities } from '../features/activities/api/activityApi.js';
```

**Key behaviors tested:**

1. **Auth flow:** `register()` returns `{ success, data: { user } }` → `login()` works → `getMe()` returns current user after login → `logout()` clears session → `getMe()` throws after logout
2. **Profile flow:** `createProfile()` with valid data → `getProfile()` reads it back → `updateProfile()` mutates it
3. **Food flow:** `searchFoods('chicken')` returns results → `createCustomFood()` creates custom entry → `logFood()` logs an entry → `getDailySummary()` returns summary → `getDailyLogs()` returns entries → `getLogHistory()` returns history → `getRecentFoods()` returns recent
4. **Activity flow:** `getRecommendations()` returns activities → `getAllActivities()` returns all activities

**Environment setup:**
- Set `VITE_API_URL=http://localhost:3001` (or use Vite proxy) via `beforeAll`
- The backend's FRONTEND_URL must match the test origin for CORS
- Run the backend server on port 3001 before the test suite

**Anticipated issue — CORS with fetch in Node:**
Since Vitest runs in Node (not browser), CORS is not enforced by default (no browser security model). The `credentials: 'include'` in http.js works because Node's fetch implementation doesn't enforce CORS. However, `Set-Cookie` may not be stored automatically in Node's fetch. **Solution:** Test the request/response contract (status codes, response body shapes) rather than cookie persistence. Use the backend supertest integration test (Task 1) for full cookie-jar auth flow.

### Verify

```bash
# Terminal 1: Start backend + Podman MySQL
cd backend
podman-compose up -d mysql
node src/server.js  # runs on port 3001

# Terminal 2: Run frontend integration test
cd frontend
npx vitest run src/__tests__/api-integration.test.js
```

### Done

- [ ] `frontend/src/__tests__/api-integration.test.js` created
- [ ] All 4 frontend API modules exercised with at least one test call each
- [ ] Tests verify response shape `{ success: true, data: ... }` matches the backend's API contract
- [ ] `vitest run` passes for the integration test file

## Must-Haves (Goal-Backward)

**Truths that must be observable:**
1. All 16 backend endpoints return correct HTTP status codes and response shapes
2. Auth-required endpoints reject unauthenticated requests with 401
3. Validation-error scenarios return 400 with descriptive messages
4. Frontend API modules correctly construct requests and parse responses
5. Podman MySQL lifecycle (start/stop) works reliably for test isolation

**Artifacts required:**
- `backend/tests/integration/api.test.js` — Backend endpoint tests
- `backend/tests/integration/helpers.js` — DB lifecycle + test utilities
- `frontend/src/__tests__/api-integration.test.js` — Frontend API layer tests

**Key links (fragile connections):**
- `auth.controller.js` `cookieOptions` → test cookie response header parsing
- `auth.middleware.js` cookie-based JWT → supertest `agent` cookie jar → frontend `credentials: 'include'`
- Podman `docker-compose.yml` MySQL healthcheck → test `beforeAll` wait loop
- `init.sql` seed data → food/activity search queries returning results
- Frontend `http.js` `apiFetch` → backend `app.js` CORS + JSON parsing

## Execution Order

1. **Task 1 first** (backend integration tests — validates the API contract independently)
2. **Task 2 second** (frontend API layer — relies on backend being up)

For Task 2, the backend must be running separately (started in a different terminal or via `beforeAll` with child_process). For a streamlined experience, the Task 1 test can be run first to validate backend, then backend stays running while Task 2 runs.

## Notes

- Podman on Windows: use `podman-compose` or `docker-compose` (whichever is available). The plan uses `podman-compose` commands but the helper should detect and fall back.
- Node `fetch()` is available natively in Node 18+ (the project uses `--experimental-vm-modules` for Jest, suggesting modern Node).
- Supertest's `agent` automatically manages `Set-Cookie` → `Cookie` forwarding, which mirrors the frontend's `credentials: 'include'` behavior.
