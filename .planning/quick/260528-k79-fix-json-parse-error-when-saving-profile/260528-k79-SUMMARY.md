# Quick Task 260528-k79: Fix JSON parse error when saving profile from frontend with Google OAuth

**Bilateral fix: rate limiter returns `{ success, error }` JSON envelope; apiFetch checks content-type before `.json()`**

## Performance

- **Completed:** 2026-05-28T12:47:00Z (approx)

## Accomplishments

- Backend `createRateLimiter` now wraps the human-readable `message` string inside a `{ success: false, error: { message, code: 'RATE_LIMITED' } }` JSON object — `express-rate-limit` auto-sets `Content-Type: application/json` and HTTP 429
- All 4 rate limiter call sites (auth, profile, food, activity) inherit the JSON envelope automatically — no call-site changes needed
- Frontend `apiFetch()` now checks the `content-type` response header before calling `.json()` — non-JSON responses (rate limiter plain text, server error HTML) are handled via `.text()` without crashing with `SyntaxError`
- Non-JSON error responses now throw immediately with the raw text, ensuring errors are surfaced rather than silently swallowed

## Decisions Made

- **Bilateral approach**: Both backend and frontend are fixed — the backend sends JSON from all rate limiters so the error is parseable, and the frontend defensively handles any non-JSON response as a fallback. This covers the known failure path (rate limiter) and unknown edge cases (HTML error pages, proxy responses).
- **No new dependencies**: The fix uses only built-in APIs (`response.headers`, `response.text()`, `response.json()`) and the existing `express-rate-limit` behavior (object `message` → JSON content-type).
- **express-rate-limit auto-detection**: When `message` is an object (not a string), `express-rate-limit` automatically sets `Content-Type: application/json` and serializes the object as JSON — no additional configuration needed.
