# Phase v1.4: Code Review Report

**Reviewed:** 2026-05-31T21:00:00Z
**Depth:** standard
**Files Reviewed:** 22
**Status:** issues_found

## Summary

Reviewed 22 files implementing the v1.4 LLM Food Recommendations feature (phases 18-23). Found two critical defects that would prevent the LLM-generated meal plan from ever working in production, plus several warnings around code quality and test coverage.

The most critical issue is a fundamental data format mismatch between the LLM prompt (which tells the LLM to output `meals` as an **object** with keys `breakfast/lunch/dinner/snack`) and every piece of processing code (which expects `meals` to be an **array** of `{meal_type, items, total_calories}` objects). This means every LLM-generated plan would fail validation and the system would silently fall back to the template-based plan — the AI feature becomes dead code.

## Critical Issues

### CR-01: Data Format Mismatch — LLM prompt defines meals as object, all processing code expects array

**Severity:** critical
**Affected files:**
- `backend/prompts/meal-plan-prompt.md` (lines 18–58)
- `backend/src/services/mealPlan.service.js` (lines 36, 40, 44, 48, 52, 112–116, 127–170)
- `backend/src/controllers/mealPlan.controller.js` (lines 111–112)
- `frontend/src/features/meal-plan/components/DayMealCard.jsx` (line 56)
- `frontend/src/features/meal-plan/components/MealPlanPage.jsx` (lines 104–106)

**Issue:**
The LLM prompt at `meal-plan-prompt.md` line 18 defines the `meals` field as an object:
```json
"meals": {
  "breakfast": [ ... ],
  "lunch": [ ... ],
  "dinner": [ ... ],
  "snack": [ ... ]
}
```

However, every piece of code that processes the plan expects `meals` to be an array:
```js
// validateMealPlanStructure (line 40)
if (day.meals.length !== 4)

// And iterates with forEach: day.meals.forEach(...)
```

Since `day.meals` is an object (not an array), `!Array.isArray(day.meals)` triggers an error at line 36–38 (`"meals" must be an array`). Every day in the plan is rejected.

Consequences:
1. `validateMealPlanStructure` fails on every LLM-generated plan — the AI feature is effectively dead code
2. `validateAndFixMealPlan` silently skips recalculation (`Array.isArray` returns false for objects)
3. `recalculateDayCalories` silently skips recalculation (same check)
4. `logDay` controller crashes with `TypeError: day.meals is not iterable` (for...of loop on object)
5. Frontend `DayMealCard` and `MealPlanPage` crash because objects don't have `.map()`
6. The `generateFallbackMealPlan` (which correctly uses array format) would always be used instead of LLM output

**Fix:**
Option A (recommended — change prompt to match code): Update `meal-plan-prompt.md` to show `meals` as an array:
```json
"meals": [
  {
    "meal_type": "breakfast",
    "items": [
      { "food_id": <integer>, "food_name": "...", "portion_grams": <integer>, "meal_type": "breakfast" }
    ]
  }
]
```
And update the example JSON in the prompt to match this array format.

Option B (transform layer): Add a normalization function in `mealPlan.service.js` that converts object-format meals to array-format before validation:
```js
function normalizeMeals(plan) {
  if (!plan || !Array.isArray(plan.days)) return plan;
  for (const day of plan.days) {
    if (day.meals && !Array.isArray(day.meals) && typeof day.meals === 'object') {
      day.meals = Object.entries(day.meals).map(([mealType, items]) => ({
        meal_type: mealType,
        items: items.map(i => ({ ...i, meal_type: mealType })),
        total_calories: items.reduce((s, i) => s + (i.calories || 0), 0),
      }));
    }
  }
  return plan;
}
```
And call this before validation in `generateMealPlan` and `regenerateDay`.

### CR-02: Meal plan correction uses wrong prompt file (activity-generic instead of meal-specific)

**Severity:** critical
**File:** `backend/src/services/mealPlan.service.js` (line 1 and line 355)
**Supporting files:**
- `backend/prompts/meal-correction-prompt.md` (created but unused)
- `backend/prompts/correction-prompt.md` (activity-plan instructions, incorrectly used)

**Issue:**
`mealPlan.service.js` imports `buildCorrectionPrompt` from `./llm.service.js`, which loads `correction-prompt.md` — a generic file designed for activity plan correction:
```
- Use ONLY activity names from the originally provided list
- Duration must be between 10-180 minutes
```

The dedicated `meal-correction-prompt.md` file was created with meal-specific rules:
```
- Use ONLY food names from the originally provided Available Foods list
- `food_name` must match exactly (case-sensitive)
- Exactly 7 consecutive days starting from the original week start date
- EVERY day MUST have exactly 4 meal slots: breakfast, lunch, dinner, snack
- Each meal slot MUST have 1-4 food items
- `portion_grams` MUST be an integer between 10 and 500
- Daily total calories should be within 80-120% of the user's daily calorie target
```

Since the activity correction prompt doesn't guide the LLM on meal plan constraints (food names, portion limits, meal slots), correction attempts will likely fail, triggering further fallback.

**Fix:**
Add a meal-plan-specific `buildMealPlanCorrectionPrompt` to `mealPlan.service.js` that loads `meal-correction-prompt.md`:

```js
// In llm.service.js or mealPlan.service.js:
export function buildMealPlanCorrectionPrompt(validationErrors) {
  return buildPrompt('meal-correction-prompt.md', {
    validationErrors: validationErrors.join('\n'),
  });
}
```

Then update `generateMealPlan` in `mealPlan.service.js`:
```js
import { buildMealPlanCorrectionPrompt } from './llm.service.js';
// ...
const correctionPrompt = prompt + '\n\n' + buildMealPlanCorrectionPrompt(lastErrors);
```

### WR-04: Partial transaction risk in logDay — items logged but plan not marked

**Severity:** warning
**File:** `backend/src/controllers/mealPlan.controller.js` (lines 127–128)

**Issue:**
The `logDay` handler calls `batchLogItems` and `markItemsLogged` in sequence without wrapping them in a single database transaction. If `batchLogItems` succeeds (inserting food log rows) but `markItemsLogged` fails (e.g., network issue, constraint violation), the food items are logged but the plan's `logged` flags are never updated. This creates an inconsistent state where:
- The food log has the entries
- The plan still shows items as unlogged
- The user could click "Log This Day" again and log duplicates

**Fix:**
Either wrap both operations in a single transaction, or make `markItemsLogged` part of the same upsert that `batchLogItems` performs. Pass a `client` from `pool.connect()` to both operations:
```js
const client = await pool.connect();
try {
  await client.query('BEGIN');
  const inserted = await batchLogItemsWithClient(client, userId, items);
  await markItemsLoggedWithClient(client, userId, weekStart, dayIndex, mealType);
  await client.query('COMMIT');
  // ...
} catch (err) {
  await client.query('ROLLBACK');
  throw err;
} finally {
  client.release();
}
```

### INF-03: `pickRandom` uses non-uniform shuffle

**Severity:** info
**File:** `backend/src/services/mealPlan.service.js` (lines 210–213)

**Issue:**
The `pickRandom` function uses `arr.sort(() => Math.random() - 0.5)` which is a known anti-pattern for shuffling. The distribution is not perfectly uniform and for a sort-based shuffle, the comparison function must be consistent (a < b ⇒ -1, a > b ⇒ 1), but `Math.random() - 0.5` is not a consistent comparator, which can cause undefined behavior in sort implementations.

**Fix:**
Use the Fisher-Yates shuffle for even distribution and correctness in fallback plan generation:
```js
function pickRandom(arr, count) {
  const copy = [...arr];
  for (let i = copy.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [copy[i], copy[j]] = [copy[j], copy[i]];
  }
  return copy.slice(0, count);
}
```
