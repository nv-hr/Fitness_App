# Phase 13: Database Schema & Foundation — Context

**Gathered:** 2026-05-29
**Status:** Ready for planning

<domain>
## Phase Boundary

Create `activity_logs` and `weekly_plans` tables, install `openai@^6.1.0` and `node-cache@^5.1.2` npm packages. This is infrastructure — no user-facing features. The tables enable Phases 14 (Activity Logger) and 15-16 (LLM Weekly Plans).

**Success criteria (from ROADMAP.md):**
1. `activity_logs` table exists with columns: id, user_id, activity_id, duration_min, intensity (ENUM), logged_date, created_at, with FK to activities and users
2. `weekly_plans` table exists with JSONB `plan_data` column and UNIQUE constraint on (user_id, week_start)
3. `intensity_level` ENUM exists with values: light, moderate, vigorous
4. Old `user_activity_log` table is cleanly dropped (data loss acceptable — seed-only data)
5. `openai@^6.1.0` and `node-cache@^5.1.2` install without dependency conflicts and are importable
</domain>

<decisions>
## Implementation Decisions

### Schema Change Approach
- **D-01:** Update `backend/db/schema.sql` in-place with new tables + ENUM. This maintains the current single-source-of-truth pattern.
- **D-02:** Create a separate `backend/db/cleanup-user-activity-log.sql` cleanup script for dropping `user_activity_log`. Keeps the destructive DROP operation explicit and visible rather than buried in the main schema file.

### weekly_plans JSONB Schema
- **D-03:** `plan_data` uses an expanded format storing activity names alongside IDs:
  ```json
  {
    "days": [
      {
        "date": "2026-06-01",
        "activities": [
          { "activity_id": 1, "name": "Push-up", "duration_min": 10, "intensity": "moderate" }
        ]
      }
    ],
    "generated_at": "2026-05-29T12:00:00Z",
    "llm_model": "openai/gpt-4o"
  }
  ```
  Self-describing so frontend can render without extra joins.
- **D-04:** Add a `status` TEXT column to `weekly_plans` with values: `active`, `generating`, `fallback`, `unavailable`. Enables Phase 16 frontend to show loading/fallback states.

### Package Version Strategy
- **D-05:** Keep caret ranges (`openai@^6.1.0`, `node-cache@^5.1.2`) for automatic minor/patch updates.
- **D-06:** Add `"engines": { "node": ">=18" }` to `package.json` and a Node.js version check in the Dockerfile, since openai@^6.1.0 requires Node >= 18.

### Migration Execution Method
- **D-07:** Apply schema changes via Supabase SQL Editor (manual execution). `schema.sql` remains the canonical source of truth — SQL Editor is the execution mechanism, not a separate migration tool.
- **D-08:** Add a `db:verify` npm script that compares local schema.sql structure against the live Supabase database to detect drift.

### activity_logs Calories Column
- **D-09:** Add `calories_burned` INT column to `activity_logs`, pre-calculated at insert time.
- **D-10:** Intensity multiplier formula: `light=0.7`, `moderate=1.0`, `vigorous=1.3`.
  Formula: `activity.estimated_calories * (duration_min / activity.duration_min) * intensity_multiplier`
</decisions>

## Existing Code Insights

### Reusable Assets
- Repository pattern with pg queries (`backend/src/repositories/*.repository.js`) — consistent error wrapping with AppError, $1 placeholders
- Database config (`backend/src/config/database.js`) — pg Pool with SSL, ready for new queries
- `DO $$ ... END $$` blocks for idempotent ENUM creation (from Phase 09 pattern) — can reuse for `intensity_level` ENUM

### Established Patterns
- Schema defined in `schema.sql`, seed data in `seed.sql`, both run via psql/SQL Editor
- Tables use `INT GENERATED BY DEFAULT AS IDENTITY` for primary keys
- Foreign keys use `ON DELETE CASCADE` for user-related data
- All tables include `created_at TIMESTAMPTZ DEFAULT NOW()`

### Integration Points
- Activity logging endpoint will query `activities` table (existing) → insert into `activity_logs` (new) — both in Phase 14
- LLM plan generation will write to `weekly_plans` (new) — Phase 15
- Frontend daily summary will need to SUM `activity_logs.calories_burned` by `logged_date` — Phase 14
</code_context>
