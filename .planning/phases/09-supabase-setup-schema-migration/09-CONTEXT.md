<decisions>
## Implementation Decisions

### Supabase Project Setup
- **D-01:** Use **Supabase CLI** (`supabase init`, `supabase link`) for project creation and linking — scriptable, repeatable, version-controlled
- **D-02:** Commit the `supabase/` folder (config.toml, project ref) to the repository
- **D-03:** Schema migration applied via **manual SQL execution** (not `supabase db push`) — full control over PostgreSQL-specific translation
- **D-04:** Use **Supabase Free Tier** — upgrade if needed later

### Connection Verification
- **D-05:** Install **pg (node-postgres)** package in `package.json` during this phase — it's needed for Phase 10 anyway
- **D-06:** Create a **standalone verify script** at `scripts/verify-supabase-connection.js` — one-shot script that loads env, connects via pg Pool, runs `SELECT 1`, logs success. Do NOT modify `server.js` startup (that rewrite belongs in Phase 10)
- **D-07:** Use **`DATABASE_URL`** (single connection string) for Supabase PostgreSQL connection — standard PostgreSQL approach

### PostgreSQL Schema Translation
- **D-08:** Use **PostgreSQL ENUMs** (`CREATE TYPE ... AS ENUM`) for: gender, fitness_goal, activity_level, food category, meal_type
- **D-09:** Use **`GENERATED BY DEFAULT AS IDENTITY`** for auto-increment primary keys (not `SERIAL`)
- **D-10:** Use **`TIMESTAMPTZ`** (`TIMESTAMP WITH TIME ZONE`) for all timestamp columns — `DEFAULT NOW()` for created_at
- **D-11:** **Application-managed `updated_at`** — set from Node.js code on update operations (no PostgreSQL trigger)
- **D-12:** JSON columns (`goal_tags`, `equipment_needed`) use **`JSONB`** type with proper PostgreSQL JSON syntax

### Seed Data Migration
- **D-13:** **Manual SQL translation** — rewrite MySQL INSERTs as PostgreSQL-compatible `seed.sql` (not pgloader)
- **D-14:** JSON array literals use `'["value"]'::jsonb` syntax
- **D-15:** Execute via **`psql $DATABASE_URL -f`** — no file size limit, automatable; bypass Supabase SQL Editor 1MB limit
- **D-16:** Use **separate files** — `schema.sql` (DDL: CREATE TYPE, CREATE TABLE, indexes) and `seed.sql` (INSERT statements)

### Locked Decisions from Prior Phases
- No Supabase Auth — keep existing JWT + Google OAuth (REQUIREMENTS.md Out of Scope)
- No Row Level Security (RLS) — server-side-only architecture
- No ORM — continue with raw SQL repository pattern (pg driver)
- Docker simplification is Phase 11 — not this phase

### the agent's Discretion
- Exact file location of `schema.sql` and `seed.sql` (within `backend/db/` vs `supabase/` directory) — planner decides based on project layout
- PostgreSQL connection pool config (min/max connections, idle timeout) for the verify script
- Whether to include password in `DATABASE_URL` or use `.env` file with Supabase connection details shared separately

</decisions>

### Established Patterns
- Repository pattern with 4 repositories (food, activity, profile, user) — each imports `pool` from `database.js`. Phase 10 rewrites these to pg syntax.

- All timestamps use `DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` — Phase 9 moves to `TIMESTAMPTZ DEFAULT NOW()` with application-managed updates.

- `backend/src/server.js` — Not modified in Phase 9. Server startup verification handled by the standalone verify script.
- `docker-compose.yml` — 4 services currently (mysql, adminer, backend, frontend). MySQL and Adminer removed in Phase 11.
- `backend/.env` — New `DATABASE_URL` env var added for Supabase connection. Existing MySQL env vars (`DB_HOST`, `DB_PORT`, etc.) stay for now, removed in Phase 10.

<specifics>
## Specific Ideas

- verify-supabase-connection.js should accept DATABASE_URL from .env and log "Supabase connected successfully" on success, exit with code 1 on failure
- schema.sql should be idempotent: `CREATE TYPE IF NOT EXISTS` and `CREATE TABLE IF NOT EXISTS` patterns
- seed.sql should be re-runnable: `TRUNCATE ... CASCADE` before INSERTs, or use `ON CONFLICT DO NOTHING`
- The 1MB Supabase SQL Editor limit (from STATE.md blocker) is avoided by using `psql` CLI for seeding
- PostgreSQL ENUMs are created before tables that reference them (CREATE TYPE before CREATE TABLE)
- The existing MySQL schema uses `TINYINT(1)` for `pdp_consent` and `is_custom` — these become `BOOLEAN` in PostgreSQL
- MySQL `LAST_INSERT_ID()` in user.repository.js → `RETURNING id` (but this rewrite is Phase 10)

</specifics>
