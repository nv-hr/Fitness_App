## Layout

### Visual Hierarchy
- **Primary focal point:** The page title "Weekly Activity Plan" at the top
- **Secondary focal area:** Vertically stacked day cards as the main content
- **Tertiary action:** "Regenerate Day" buttons inside expanded cards

### Page Structure

Full-page view at path `/weekly-plan`. Uses the existing `ResponsiveLayout` wrapper (max-width 600px, auto margin, responsive padding per `useResponsive`).

### States Overview

| State | Display |
|-------|---------|
| **Loading** (first visit) | Full-page "Loading..." centered text, same as existing pattern |
| **Empty** (no plan exists) | Explanation text + "Generate My Weekly Plan" button calling POST /generate |
| **Generating** (first-time) | Full-page loading state: spinner text "Generating your plan..." |
| **Active** (plan exists) | Day-by-day cards, collapsed by default |
| **Regenerating day** | Only that day card shows loading spinner in place of regenerate button |
| **Fallback** (LLM unavailable) | Same card layout as active plan + muted banner: "Using a backup plan. Some activities may differ from your preferences." |
| **Rate-limited** | Regenerate button shows "Wait 4:32" ticking countdown, disabled |
| **Error** (fetch failed) | Error message + "Try Again" action |

## Components Inventory

### 1. WeeklyPlanPage (orchestrator)
- Path: `frontend/src/features/weekly-plan/components/WeeklyPlanPage.jsx`
- Pattern: useState + useEffect orchestrator (identical to ActivitiesPage.jsx)
- Manages: `plan`, `loading`, `error`, `generating`, `regeneratingDay`, `rateLimitCountdown`
- Calls: `getWeeklyPlan()`, `generateWeeklyPlan()`, `regenerateDay()` from API module
- Renders: header, error/success/loading states, DayCard list
- **Backend dependency:** GET endpoint `GET /api/weekly-plans?weekStart=YYYY-MM-DD` and regenerate-day endpoint must exist (both planned as part of this phase per CONTEXT.md D-02, D-09)

### 2. DayCard (day plan card)
- Collapsed state: day name (e.g., "Monday, May 25"), summary ("2 activities · 60 min total"), ▼ expand indicator
- Expanded state: full activity list + "Regenerate Day" button + ▲ collapse indicator
- Each card manages its own `isExpanded` state independently (D-08)
- Click on header toggles expand/collapse
- Follows exact pattern of `ActivityHistory.jsx` (existing component) — clickable header with ▲/▼

### 3. DayActivityRow (single activity within a day)
- Display: activity name · duration ("30 min") · intensity label (color-coded)
- No actions on individual activity rows (one-click plan-to-log is deferred to v2)

### 4. RateLimitedButton (regenerate button with countdown)
- Normal state: "Regenerate Day" — green accent, full-width inside expanded card
- Loading state: spinner text "Regenerating..." — disabled (opacity 0.6, cursor not-allowed)
- Rate-limited state: "Wait 2:30" — disabled, countdown ticks every second (D-10, D-11)
- The retryAfter value comes from the 429 response error object (D-12)
- Button re-enables automatically when countdown reaches 0 (D-13)
- No separate banner notification — button state alone communicates the limit (D-12)

### 5. EmptyStatePlan
- Heading: "No Weekly Plan Yet"
- Body: "Generate a personalized weekly activity plan based on your profile and recent activity history."
- CTA: "Generate My Weekly Plan" button (calls POST /generate)
- Loading spinner text: "Generating your plan..." while first generation is running

### 6. FallbackBanner
- Text: "Using a backup plan based on your activity history. Some activities may differ from your preferences."
- Background: `#fffbew` (amber-50), text: `#92400e`
- Placed at top of plan display when plan status is `fallback` or `unavailable`

## Interaction Specifications

### Expand/Collapse
- Click on day header toggles expanded state
- Only one card can be expanded at a time? **No** — each card manages independent state (D-08)
- No animation on expand/collapse (no CSS transitions in existing codebase — follow existing pattern)

### Regeneration Flow
1. User expands a day card
2. Clicks "Regenerate Day" button
3. Button changes to "Regenerating..." (disabled) — only that card is affected
4. On success: plan data for that day updates, button returns to "Regenerate Day"
5. On 429 error: button enters countdown state showing "Wait N:NN" from response `error.retryAfter`
6. Countdown ticks every 1 second via `setInterval`, decrementing the `retryAfter` value
7. When countdown reaches 0: button re-enables to "Regenerate Day"
8. On other errors: display error message above the card
9. **Backend dependency:** POST endpoint for single-day regeneration must exist (D-09)

### First Generation Flow
1. User navigates to `/weekly-plan`
2. If no plan exists (empty state): show EmptyStatePlan component
3. User clicks "Generate My Weekly Plan"
4. Full-page loading state: "Generating your plan..."
5. On success: render DayCard list
6. On 429: show rate-limit message + countdown (same timer pattern, but full-page)
7. On other error: show error state with retry

### Plan Data Refresh
- GET endpoint is called on page mount to check for existing plan
- No auto-refresh — user must navigate away and back or trigger regeneration
- After successful regeneration of a day, the plan data for that day is updated in-place (no full page reload)

### Rate Limit Handling
- `retryAfter` field from 429 response is the **source of truth** (D-11)
- Client-side countdown is a visual timer only — never independently calculated
- If response has `retryAfter: 150`, the countdown starts at 150 seconds (2:30)
- Timer decrements every 1000ms
- No localStorage/cookie for persisting rate limit across sessions — limit is session-only (existing rate limiter uses in-memory store)

## API Contract

### New endpoints needed (backend additions for this phase)

| Method | Endpoint | Purpose | Rate-limited? |
|--------|----------|---------|---------------|
| GET | `/api/weekly-plans?weekStart=YYYY-MM-DD` | Read plan from DB/cache | No (D-02) |
| POST | `/api/weekly-plans/generate` | Generate entire plan | Yes (5/15min) |
| POST | `/api/weekly-plans/regenerate-day` | Regenerate single day | Yes (shares same limiter) |

### Response Shapes

**GET success (plan exists):**
```json
{
  "success": true,
  "data": {
    "plan": {
      "days": [
        {
          "date": "2026-05-25",
          "activities": [
            {
              "activity_id": 1,
              "name": "Running",
              "duration_min": 30,
              "intensity": "moderate"
            }
          ]
        }
      ],
      "status": "active",
      "generated_at": "2026-05-25T10:00:00.000Z"
    },
    "fromCache": true
  }
}
```

**GET success (no plan):**
```json
{
  "success": true,
  "data": {
    "plan": null,
    "fromCache": false
  }
}
```

**POST 429 (rate limited):**
```json
{
  "success": false,
  "data": {
    "plan": null,
    "fromCache": false,
    "status": "rate_limited",
    "retryAfter": 150
  },
  "error": {
    "message": "Weekly plan generation limit reached. Please try again later.",
    "code": "RATE_LIMITED",
    "retryAfter": 150
  }
}
```
