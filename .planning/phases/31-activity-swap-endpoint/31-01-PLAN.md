<objective>
Create the core service infrastructure for activity swapping: the swap-specific LLM prompt, the `swapActivity()` function in `llm.service.js` that performs single-activity replacement with LLM call and fallback, and the dedicated `swapLimiter` rate limiter.

Purpose: These three pieces form the backend engine behind the swap endpoint. The prompt tells the LLM what to generate, the service function orchestrates the swap (LLM call → validation → merge into cached plan → fallback on failure), and the rate limiter enforces the 10 req/5 min limit independent from generate/regenerate.

    1. **Role**: "You are a fitness planner selecting a replacement activity."
    2. **Context**: User's fitness goal, activity level
    3. **What's happening**: "The user wants to replace an activity in their weekly plan."
    4. **Activity being replaced**: `{{swappedActivity}}` — show what's being swapped out
    5. **Day context**: `{{dayContext}}` — which day and date
    6. **Week context**: `{{weekContext}}` — so the LLM can avoid duplicates
    7. **Available activities**: `{{availableActivities}}` — full list
    8. **Constraints**:
       - Choose a DIFFERENT activity from the one being replaced
       - Must be from the Available Activities list
       - Must align with the user's fitness goal
       - Duration and intensity should match the user's activity level
       - 10-180 minutes duration
       - Valid intensity: light / moderate / vigorous
       - Estimate calories_burned

       ```json
       {
         "activity_id": <integer>,
         "name": "<exact name>",
         "duration_min": <integer>,
         "intensity": "light|moderate|vigorous",
         "logged": false,
         "calories_burned": <integer>
       }
       ```
    10. **Example**: Show a single-activity JSON example (for illustration only, not part of template).

    Use the same `{{placeholder}}` variable syntax as `weekly-plan-prompt.md` and `system-prompt.md` for consistency with `buildPrompt()`.

    The prompt should be self-contained (doesn't need the full weekly-plan-prompt content) — it only needs user context, the swapped activity, and the available activities list.

    Per D-03: Include goal-specific activity selection guidance (the same lose_weight/maintain/build_muscle rules from weekly-plan-prompt.md).

  <name>Task 2: Add swapActivity() to llm.service.js — core swap logic</name>
  <files>backend/src/services/llm.service.js</files>
  <action>
    Add a new exported async function `swapActivity(deps, activityId, dayIndex)` to `backend/src/services/llm.service.js`.

    **Function signature:**
    ```js
    export async function swapActivity(deps, activityId, dayIndex)
    ```

    Where `deps` is an object with callbacks for data fetching (consistent with `generateWeeklyPlan`/`regenerateDay` pattern):
    ```js
    {
      getProfile: (id) => findProfileByUserId(id),
      getActivityHistory: (id, days) => getActivityHistoryWithEntries(id, days),
      getActivities: () => getAllActivities(),
      getTopActivities: (id, limit) => getTopActivities(id, limit),
      getRandomActivity: (goalTags) => getRandomActivities(goalTags, 1),  // NEW callback for fallback
      userId,
      weekStart,
      availableDays,  // optional, inferred from plan if not provided
    }
    ```

    **Implementation logic:**

    1. **Validate inputs**: `activityId` must be a positive integer, `dayIndex` must be 0-6. Throw `AppError('ValidationError', message, 400)` for invalid inputs.

    2. **Get current plan**: Call `getCachedPlan(userId, weekStart)`. If the plan is null/undefined, throw `AppError('NotFoundError', 'No weekly plan found for this week', 404)`.

    3. **Locate the activity**: Navigate `plan.days[dayIndex]`. Validate it exists and is not a rest day. Find the activity index by matching `activity_id`. If not found → throw `AppError('ValidationError', 'Activity not found in current plan', 400)`.

    4. **Fetch user data**: Use `Promise.all` to fetch profile, activity history (14 days), and all activities from deps. If profile is null, still proceed (prompt builder handles it — the prompt has {{fitnessGoal}} and {{activityLevel}} which can default).

    5. **Build context strings for the swap prompt**:
       - `swappedActivity` string: `"${act.name} (${act.duration_min} min, ${act.intensity}, ${act.calories_burned || '?'} cal)"`
       - `dayContext` string: `"Day ${dayIndex + 1} (${plan.days[dayIndex].date})"`
       - `weekContext` string: Count activity days and rest days: `"${activityDayCount} activity days, ${restDayCount} rest days"`
       
       Build comma-separated `availableActivities` text in the same format as `buildSystemPrompt()`: `"- ${a.name} (${a.estimated_calories} cal, ~${a.duration_min}min)"`

    6. **Build swap prompt**: Call `buildPrompt('activity-swap-prompt.md', { ... })` with all template variables.

    7. **Call LLM**: 
       ```js
       let replacement;
       try {
         replacement = await callLlmApi(prompt);
       } catch (err) {
         // Fallback: pick random activity from database via deps callback
         const fallbackActs = await deps.getRandomActivity(goalTags || ['maintain']);
         if (fallbackActs && fallbackActs.length > 0) {
           replacement = {
             activity_id: fallbackActs[0].id,
             name: fallbackActs[0].name,
             duration_min: fallbackActs[0].duration_min || 30,
             intensity: 'moderate',
             logged: false,
             calories_burned: fallbackActs[0].estimated_calories || 100,
           };
         } else {
           throw new AppError('SwapFallbackError', 'No fallback activity available', 500);
         }
       }
       ```

       The `goalTags` for fallback should be derived from `profile.fitness_goal`:
       - `'lose weight'` → `['lose_weight']`
       - `'build muscle'` → `['gain_weight']`
       - `'maintain'` → `['maintain']`
       - default → `['maintain']`

    8. **Validate replacement activity**: Use `validateActivities([replacement], 'Swap, ')` to check structure. If invalid, fallback to random activity as above.

    9. **Fuzzy-match activity name**: Call `fuzzyMatchActivityName(replacement.name, dbActivities)` to resolve the activity name to a database activity. This ensures the replacement's `activity_id` and `name` match a real database row. Apply the same fix as `validateAndFixPlan` does for full plans.

    10. **Merge into plan**: Deep-clone the plan (JSON parse/stringify). Replace `plan.days[dayIndex].activities[activityIndex]` with the validated replacement.

    11. **Update cache**: Call `setCachedPlan(userId, weekStart, JSON.parse(JSON.stringify(mergedPlan)))`.

    12. **Return result**:
        ```js
        return {
          plan: mergedPlan,
          day: mergedPlan.days[dayIndex],
          dayIndex,
          activityIndex,
          replacement,
          fromCache: false,
          status: 'active',
        };
        ```

    **Error handling per decisions:**
    - No plan found → 404 (AppError)
    - Activity not found in plan → 400 "Activity not found in current plan"
    - LLM failure → fallback to random DB activity (no error to user)
    - Re-swapping same slot is allowed (normal flow)

    **Old-format compatibility per D-34:**
    The function works on any plan that has a `days` array with activities. Old-format plans (without `rest_day`, `format_version`) already have `days[dayIndex].activities` — no special handling needed. The swap does not touch `rest_day` or `format_version` fields.
