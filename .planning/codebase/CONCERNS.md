### 2. In-memory cache loss on server restart

**Issue:** The in-memory `NodeCache` (line 48 of `llm.service.js`) and the `migrationFailCooldown` Map (line 19 of `weeklyPlan.controller.js`) are lost on every server restart. The `planCache` expires plans after 1 hour TTL, but the cooldown state is purely in-memory.

**Files:**
- `backend/src/services/llm.service.js` (line 48)
- `backend/src/controllers/weeklyPlan.controller.js` (line 19)

**Impact:** After a production restart, all cached plans must be regenerated by the LLM, causing:
- Long response times for the first user requests
- Multiple LLM API calls for active users
- Rate limits being consumed immediately after deployment

**Fix approach:** Persist the plan cache to the database (already has `weekly_plans` table for this) or use Redis. The DB persistence path already exists in `weeklyPlan.repository.js` — but the code prefers in-memory cache and only falls back to DB.

## Known Bugs

### 1. OpenRouter API key logged in plaintext at startup

**Issue:** `backend/src/services/llm.service.js` (lines 14-18) reads the `OPENROUTER_API_KEY` and logs a console error mentioning it when the key is missing. While this doesn't log the key value itself, the error message includes the env var name, and the startup log (line 46) prints the model names being used — not a key leak but verbose.

**Root cause:** The more critical issue is that the API key is stored in `process.env` and referenced directly without any obfuscation or secrets manager. If the process environment is compromised, the key is exposed.

### 2. `new Date()` used without timezone normalization in date comparisons

**Issue:** Multiple controllers use `new Date().toISOString().split('T')[0]` for "today" as a date boundary check. When the server is in a timezone behind UTC, a user's local "today" may differ from the server's "today".

**Files (partial list):**
- `backend/src/controllers/food.controller.js` (lines 65, 68)
- `backend/src/controllers/activity.controller.js` (lines 52, 55)
- `backend/src/controllers/weeklyPlan.controller.js` (line 246)
- `backend/src/controllers/dailyMealPlan.controller.js` (line 16)

**Impact:** Users in UTC-negative timezones (e.g., America) may be unable to log food or activities for their current local date after UTC passes midnight. A user in New York at 8 PM EST (midnight UTC) would be blocked from logging.

**Workaround:** None — users must wait until their local midnight when UTC catches up.

**Fix approach:** Use a timezone-aware approach — either normalize to the user's timezone via frontend-supplied date, or store and compare using local dates only.

### 3. `ssl: false` in database pool config

**Issue:** `backend/src/config/database.js` (line 22) sets `ssl: false` for the PostgreSQL connection pool. Supabase requires SSL connections for production databases. The comment (lines 13-18) notes session mode (port 6543) works when `ssl.rejectUnauthorized` is disabled, but the actual code does not use SSL at all.

**Files:**
- `backend/src/config/database.js` (line 22)

**Impact:** In production, the database connection may be rejected by Supabase for not using SSL, or the connection may be unencrypted (man-in-the-middle risk).

**Fix approach:** Enable SSL with `rejectUnauthorized: false` for Supabase, or conditionally enable SSL in production.

### 4. Fallback plan uses `calorieTarget: 2000` hardcoded

**Issue:** When profile data fetch fails in `generateMealPlan` and `generateFallbackMealPlan`, the code defaults to a `2000` calorie target (lines 320-321, 324 of `mealPlan.service.js`; line 260 of `dailyMealPlan.service.js`).

**Files:**
- `backend/src/services/mealPlan.service.js` (lines 320, 324)
- `backend/src/services/dailyMealPlan.service.js` (line 260)

**Impact:** A user whose profile data fails to load will receive a meal plan based on a generic 2000-calorie target regardless of their actual needs.

**Fix approach:** Cache the last-known calorie target per user in the profile table, or use population averages based on age/gender/weight.

### 5. Integration test helper references missing SQL files

**Issue:** `backend/tests/integration/helpers.js` (lines 22-23) references `schema.sql` and `seed.sql` at `backend/db/schema.sql` and `backend/db/seed.sql`, but no SQL files exist in the repository.

**Files:**
- `backend/tests/integration/helpers.js` (lines 22-23)
- `backend/package.json` line 15: `"db:migrate": "psql \"$DATABASE_URL\" -f db/drop_user_activity_log.sql -f db/schema.sql -f db/seed.sql"`

**Impact:** Integration tests and DB migration scripts will fail because the referenced SQL files are missing. The scripts `db/schema.sql`, `db/seed.sql`, and `db/drop_user_activity_log.sql` do not exist.

## Security Considerations

### 1. CORS allows `null` origin via FRONTEND_URL parsing

**Issue:** In `app.js` (lines 31-44), the `parseFrontendUrl()` function falls back to `'http://localhost:3000'` when `FRONTEND_URL` is invalid. If a malicious actor can make the URL parsing fail, the fallback is still a valid origin — but the real risk is that `cors()` is configured with a single origin string, not a whitelist.

**Files:**
- `backend/src/app.js` (lines 31-84)

**Impact:** The CORS origin is a single frontend URL. In development, this is fine. However, if the app is ever accessed from a custom domain, CORS must be updated manually.

**Risk:** Low — current config is standard for SPA deployments.

### 2. Auth cookie is set with `sameSite: 'none'` allowing cross-site requests

**Issue:** `backend/src/controllers/auth.controller.js` (line 12) sets `sameSite: 'none'` and `secure: true` on the httpOnly JWT cookie. The `sameSite: 'none'` setting disables CSRF protection, making the cookie sent on cross-site requests.

**Files:**
- `backend/src/controllers/auth.controller.js` (lines 9-14)

**Impact:** If the frontend URL is known, a CSRF attack could trigger authenticated API calls on behalf of a logged-in user because the browser will include the cookie.

**Current mitigation:** The CORS origin restriction limits which origins can make cross-origin requests. However, this only works in browsers that enforce CORS preflight — simple requests (GET, HEAD) with `Content-Type: text/plain` may bypass CORS checks.

**Recommendation:** Change `sameSite` to `'lax'` for most routes, or `'strict'` for auth-sensitive operations. The `'none'` setting appears to be for the separate frontend/backend deployment scenario — evaluate if `'lax'` would suffice.

### 3. Google OAuth token and refresh token discarded

**Issue:** In `backend/src/config/passport.js` (line 18), the Google OAuth callback receives `accessToken`, `refreshToken`, and `profile` from Google, but only `profile` data is used. The tokens are discarded.

**Files:**
- `backend/src/config/passport.js` (line 18)

**Impact:** The app cannot refresh the Google access token when it expires, nor can it access any Google APIs on behalf of the user (e.g., Google Fit integration, calendar sync).

**Risk:** Low — currently no Google API features beyond authentication are implemented.

### 4. No helmet CSP configuration

**Issue:** While `helmet()` is used in `app.js` (line 78), no Content Security Policy is configured. The default Helmet CSP may block legitimate inline styles used by the Tailwind CSS frontend.

**Files:**
- `backend/src/app.js` (line 78)

**Impact:** The default helmet CSP may cause frontend resources to be blocked. However, no CSP-related issues were observed — likely because helmet's default CSP is permissive enough for Tailwind.

## Performance Bottlenecks

### 1. `ORDER BY RANDOM()` in production queries

**Issue:** `backend/src/repositories/activity.repository.js` (line 16) uses `ORDER BY RANDOM()` in the `getRandomActivities` function. This causes PostgreSQL to perform a full table scan and sort on every call, which becomes expensive as the activities table grows.

**Files:**
- `backend/src/repositories/activity.repository.js` (line 16)

**Impact:** With 200+ activities, each call to `getRandomActivities` requires PostgreSQL to compute a random value for every row and sort them. The rate limiter (`max: 20` requests per minute at `/api/activities`) mitigates this but does not solve the underlying inefficiency.

**Fix approach:** Use a more efficient random selection method — e.g., `SELECT * FROM activities WHERE goal_tags ?| $1 OFFSET floor(random() * (SELECT count(*) FROM activities WHERE goal_tags ?| $1)) LIMIT $2`, or use a client-side shuffle after fetching a small sample.

### 2. Full food list sent in LLM prompts

**Issue:** `buildMealPlanPrompt` in `backend/src/services/mealPlan.service.js` (lines 159-177) builds a text representation of all foods in the database and passes it to the LLM. For a large food database, this can exceed LLM token limits. The code has a truncation safety net (lines 162-177), but 150 foods is still very large.

**Files:**
- `backend/src/services/mealPlan.service.js` (lines 159-177)
- `backend/src/services/dailyMealPlan.service.js` (lines 78-95)

**Impact:** Each meal plan generation sends a large prompt to the LLM API, consuming tokens and increasing latency and cost.

**Fix approach:** Send only a curated subset of foods (e.g., most frequently logged foods, seasonal foods) instead of the full database. The truncation logic is a good start but could be smarter.

### 3. Memory leak risk in per-user lock Map

**Issue:** `backend/src/services/llm.service.js` (line 52) uses a `Map` for per-user mutexes. The `acquireLock` function (lines 54-62) sets entries but only removes them when `release()` is called. If a lock is acquired but release is never called (e.g., due to an uncaught exception), the entry persists indefinitely.

**Files:**
- `backend/src/services/llm.service.js` (lines 52, 54-62)

**Impact:** Over time, abandoned locks can accumulate, causing memory growth and preventing legitimate lock acquisitions for those keys.

**Fix approach:** Add a TTL mechanism to the lock entries (e.g., using `Map` with timestamps and a cleanup interval), or use a more robust locking library.

### 4. Deep JSON cloning in multiple hot paths

**Issue:** The codebase uses `JSON.parse(JSON.stringify(obj))` for deep cloning in many places:
- `backend/src/services/llm.service.js` (lines 320, 525, 571, 755, 766)
- `backend/src/services/mealPlan.service.js` (lines 119, 289, 419)
- `backend/src/services/dailyMealPlan.service.js` (line 217)
- And more

**Files:** Multiple files across backend services.

**Impact:** Each deep clone is O(n) on the object size. In hot paths (e.g., plan swap, toggle complete), this adds unnecessary overhead for large plan objects.

**Fix approach:** Use `structuredClone()` (modern Node.js built-in) which is generally faster, or minimize cloning by using immutable update patterns.

## Scaling Limits

### 1. Single-process Node.js server

**Issue:** `backend/src/server.js` starts a single Express process. No clustering, no worker threads, no reverse proxy configuration for horizontal scaling.

**Impact:** Under load:
- All request processing is single-threaded
- LLM API calls (30s timeout) block the event loop for other requests
- Server crashes affect all users simultaneously

**Scaling path:** Add `PM2` or Node.js `cluster` module for multi-core utilization. Implement a message queue for LLM API calls.

### 2. Shared in-memory caches tied to single process

**Issue:** `NodeCache`, `locks` Map, and `migrationFailCooldown` are all in-memory and not shared across processes.

**Impact:** If the app is scaled horizontally (multiple processes), each process has its own cache and lock state. A swap operation on one process would not be reflected in another process's cache, leading to stale data reads.

**Scaling path:** Replace in-memory caches with Redis or use the PostgreSQL database as the source of truth for all plan data.

## Dependencies at Risk

### 1. `openrouter/owl-alpha` default model

**Issue:** `backend/src/services/llm.service.js` (line 38) defaults to `openrouter/owl-alpha` as the LLM model. This appears to be an early / experimental model and may be deprecated or removed by OpenRouter at any time.

**Files:**
- `backend/src/services/llm.service.js` (line 38)

**Impact:** If the model is deprecated, existing deployed instances without a configured `LLM_MODEL` env var will fail to generate plans.

**Fix approach:** Default to a stable, well-known model (e.g., `openrouter/openai/gpt-4o-mini` or `openrouter/anthropic/claude-3-haiku`) and document the model choice. The fallback chain (`fallbackModel`, `fallbackModel2`) is a good pattern but the defaults are empty strings.

### 2. `node-cache` dependency for critical caching

**Issue:** The in-memory cache (`node-cache`) is central to application performance but has no persistence or replication story.

**Impact:** Every server restart is a "cold start" — all plans must be regenerated via LLM API calls, causing rate limit spikes and slow user experiences.

**Fix approach:** Consider replacing with `ioredis` or using the PostgreSQL table as primary cache with the in-memory cache as a fast L1 layer.
